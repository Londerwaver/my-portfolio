Agent 思考架构全景

从设计范式 → 功能模块 → 工程化任务拆解的三层拆析。范式是"怎么组装"的顶层决策，功能模块是"组装什么"的零件选择，工程拆解是"具体怎么做"的落地方法——三者层层递进，合在一起才完整定义了一个 Agent。

全景总结

三层关系一览，选型决策速查。

三层定位
层次回答的问题抽象级别对应内容
设计范式这个 Agent 整体怎么运作？最高 — 架构决策ReAct / Plan-and-Execute / Reflection

工程拆解具体怎么把任务落地执行？最底 — 实现方法静态/动态拆分 / 并行优化 / 自适应拆分 / Replan / 验证标准
一句话记住每层
  • 范式 = 你选的"户型图"（是走一步看一步，还是先规划再执行，要不要加检查环节）
  • 功能模块 = "厨房"和"烟雾报警器"这样的功能间（规划层面向未来——接下来做什么；反思机制面向过去——刚才做得怎么样）
  • 工程拆解 = "施工说明书"（每面墙怎么砌、哪些能同时开工、做不好怎么返工）
选型决策树
任务复杂吗？
├─ 否 → ReAct（够用就好）
└─ 是 → 任务流程长吗？
   ├─ 否 → ReAct + Reflection（加质量检查）
   └─ 是 → Plan-and-Execute
      ├─ 执行中常遇意外？ → + 动态 Replan
      ├─ 输出质量要求高？ → + Reflection（最多 2~3 轮）
      ├─ 需跨任务积累经验？ → + Reflexion
      └─ 步骤间有独立部分？ → 并行优化（DAG 依赖分析）

始终记住：先跑起来再优化，别为了炫技搞过度工程化。
LAYER 01

设计范式

Agent 的顶层做事流程框架——决定整个系统从头到尾按什么大逻辑跑。

核心洞察：ReAct 解决"单步灵活性"，Plan-and-Execute 解决"长任务跑偏"，Reflection 解决"输出质量不够"。三者解决的问题层次不同，选型要看任务复杂度、流程确定性、输出质量要求三个维度。

一、ReAct：单步迭代范式

本质

思考 → 行动 → 观察 → 再思考的循环，走一步看一步，每步行动完全基于上一步结果实时调整，没有提前定死的完整计划。

思考
→
行动
→
观察
↻ 循环

生活类比：外卖骑手——接单后不会提前把每步定死，而是实时根据情况做决策。路封了立刻改路线，不死守原计划。

维度说明
优势实现简单、灵活度高、逻辑透明、出了问题好排查，新手入门零门槛
短板长流程多步骤任务容易跑偏、忘了最初目标、某步陷入无效循环
适用场景流程不固定、复杂度适中的任务：信息搜索、简单问答、客服机器人

二、Plan-and-Execute：规划执行范式

本质

先把完整计划定好，再按计划一步步干。将"规划推理"和"执行推理"完全解耦，各管各的。

规划器 Planner
→
执行器 Executor
→
重规划 Re-planner
↻ 动态调整

生活类比：项目经理——接了大目标后先做完整项目规划（需求调研→原型设计→开发→测试→上线），再把每步分给对应模块执行。

三阶段流程

  1. 规划阶段：Planner 接收任务，生成有序步骤清单。只做规划，不做实际执行。
  2. 执行阶段：Executor 按清单逐步执行，每步把前面结果作为 context 传入，不会"失忆"。
  3. 重规划阶段：每步执行完后，Re-planner 回顾进展，判断原计划是否仍适用，必要时动态调整后续步骤。

隐藏优势：混合模型策略

规划和执行是独立模块，可以用不同模型。规划阶段用强模型（GPT-4）保证方向正确，执行阶段用便宜的小模型（GPT-4o-mini / 7B 开源模型）。实际项目可降低总成本 70%~90%，质量几乎不受影响。

维度说明
优势整体结构清晰、执行链路可控、不易跑偏、支持并行优化
短板灵活度不如 ReAct、实现更复杂、token 消耗增加
适用场景流程长、复杂度高的任务：竞品分析报告、项目开发、行业调研

三、Reflection：质量增强范式

关键定位：Reflection 不是独立的完整流程，而是给 ReAct 或 Plan-and-Execute 加的"质量增强 buff"。它不改变原本的做事流程，只加一层"自我检查、自我修正"环节。前两者的核心是"把事做完"，Reflection 的核心是"把事做好"。

生活类比：考试时做完一道题（或整张卷子），回头检查一遍——有没有算错数、看错题，发现错了马上改。

生成
→
评估
→
改进
↻ 直到 PASS
维度说明
优势输出质量明显提升，幻觉、逻辑错误、细节遗漏减少
代价至少多一次 LLM 调用，token 和延迟线性增加；无上限会死循环
适用场景输出质量要求极高、不能出错：生产代码、商业报告、法律文书

进阶机制

动态 Replan

解决 Plan-and-Execute"计划定死、中途遇到意外怎么办"的痛点。每步执行后，把当前结果和剩余计划交给规划模块判断是否需要调整。

代价：每步多一次"评估计划"的 LLM 调用。实践折中：设触发条件（输出与预期差异大 / 步骤失败时才触发），不是每步都 Replan。

Reflexion

把 Reflection 推到更深：不仅检查输出对不对，还把每次失败原因总结成"经验教训"存进记忆，下次遇到类似任务直接参考。

效果数据：在 HumanEval 代码生成基准上，把 GPT-4 的 pass@1 从 80% 提升到 91%，提升超 10 个百分点。

选型指南

任务特征推荐范式理由
不复杂、流程不固定、需实时调整ReAct够用就好，别搞复杂
任务长、容易跑偏、需整体结构清晰Plan-and-Execute先定计划再执行
执行中常遇意外需调整计划P&E + Replan保留结构优势，增加动态调整
输出要求高、不能出错上述 + Reflection加自我检查环节
需跨任务积累经验、避免重复犯错上述 + Reflexion沉淀失败教训
生产级常见架构：规划阶段用 Plan-and-Execute 定全局计划 → 每步执行用 ReAct 循环处理（单步可能也需多轮工具调用）→ 最后对整体输出做一次 Reflection 检查质量。三层嵌套，在 LangGraph 等框架里实现很自然。
避坑提醒：别把所有范式全堆在一起。又规划、又反思、又 Replan、又积累经验——系统又复杂又慢还容易出 bug。工程开发永远是"够用就好"，先把 ReAct 玩明白，再根据需求往上加。

LAYER 02

功能模块

范式决定了"怎么组装"，功能模块则是具体"组装什么"。每个范式内部都会用到若干功能模块，其中最重要的是规划层和反思机制。

规划层：让 LLM 把推理过程显式化

LLM 默认"一口气"生成答案，没有显式推理过程。Transformer 的 next-token 预测机制导致推理链越长、隐式跳步越多，误差越容易累积。规划能力的本质是把隐式推理过程显式化，让每步有迹可循。

CoT → ToT → GoT：层层递进的三种方案

① CoT（Chain of Thought）思维链

零成本 生产标配

在 prompt 里加一句"请一步步思考"，LLM 就会把推理过程逐步写出来。本质是"写下来的推理过程"成为后续生成的依据，帮助 LLM 不跳步。

  • Zero-shot CoT：直接加"让我们一步步思考"，不需要额外例子
  • Few-shot CoT：给几个带完整推理过程的例子，效果更稳定

局限：只有一条推理路径，一旦开头走错，整条链全错，没有任何纠偏机制。

② ToT（Tree of Thoughts）思维树

成本 3~5x 高准确率

针对 CoT"一旦走错就全错"的问题。把"一条链"变成"一棵树"：同时探索多条路径，边探索边评估边剪枝，最终选最优路径。

生成多个候选思路
→
评估可行性打分
→
剪枝保留高分
↻ 循环

代价：典型设置（3 条路径 × 2-3 层）成本是 CoT 的 3~5 倍；极端场景可能 10 倍以上。

③ GoT（Graph of Thoughts）思维图

学术阶段 生产未落地

针对 ToT"不同分支中间结论无法复用"的问题。把推理结构从树换成图，允许不同路径的中间结果合并、复用——一个节点可以接收多个前置节点的输出。

典型场景："分别研究竞品 A 和 B，再做综合对比"——树结构里"综合分析"节点只有一个父节点，无法自然汇聚两条路径的结论；图结构里这是原生支持。

三者演进关系

方案解决的问题结构工程成本
CoT要不要把推理显式化线性链几乎零成本，加一句 prompt
ToT走错方向怎么纠偏树（多路径+剪枝）3~5 倍 CoT 调用量
GoT中间结论能不能复用图（节点合并复用）学术阶段，生产未落地

工程实战：Plan-and-Execute 规划模式

CoT/ToT/GoT 讲的是"LLM 内部怎么把问题想清楚"，Plan-and-Execute 讲的是"Agent 怎么把大任务切成多个独立执行的步骤"。后者更贴近工程实践，与 ReAct 的关系是：ReAct 负责每步怎么执行，Plan-and-Execute 负责步骤的整体编排和动态调整，两者经常搭配使用。

反思机制：生成 → 评估 → 改进的闭环

来自 Self-Refine 论文（Madaan 等，2023）。核心思路是让 Agent 完成步骤或任务后，自我评估输出质量，不达标就重试或调整策略。用"草稿 → 批阅 → 修改"来类比：学生交草稿，老师批阅指出问题，学生拿着批注修改，直到通过。

两个核心 Prompt

评估 Prompt

任务：{task}
当前输出：{current_output}

请评估以上输出：
1. 有没有事实错误或逻辑问题？
2. 有没有遗漏重要内容？
3. 表达是否清晰准确？

如果输出已经足够好，回复"PASS"；
否则指出具体问题并给出改进建议。

改进 Prompt

原始任务：{task}
当前输出：{current_output}
评估意见：{reflection}

请根据评估意见改进输出：
两个关键设计：
① 明确检查维度（事实、逻辑、完整性、表达）——没有方向的评估流于表面，LLM 只会说"看起来不错"。
② PASS 机制——给 LLM"够好了就停"的出口，否则会无限挑毛病，把对的东西改错。
改进 Prompt 的关键：必须同时传入原始任务 + 原始输出 + 评估意见三者。缺任何一个都会让改进变得盲目——只有任务不知道在什么基础上改，只有输出不知道改哪里，只有评估意见可能偏离原始目标。

两个粒度：步骤级 vs 任务级

维度步骤级反思任务级反思
触发时机每个工具调用/推理步骤后立即检查整个任务执行完后整体评估
优势错误早发现早纠正，不会层层放大开销小（只多 1 次调用）；能发现整体性问题
代价10 步任务可能要调 20 次 LLM中途出错则前期工作全浪费
适用场景步骤强依赖、前一步错了后面全错步骤相对独立、整体质量更重要（如报告）

多 Agent 互评：为什么"他人审视"比"自我检查"更好

单 Agent 自我反思时，评估者和生成者是同一个模型，生成时形成的"内部逻辑"在评估时也会沿用，容易陷入"自洽"。独立的 Critic Agent 没有这种包袱，唯一职责就是"找问题"，视角更客观。

适用场景：质量要求非常高的场景——生成代码后让独立测试 Agent 验证、生成报告后让事实核查 Agent 交叉验证。代价是多一个 Agent 的调用成本和系统复杂度。

进阶反思方案

Reflexion

不仅反思当前输出，还把"失败经验"存进记忆，下次遇到类似任务直接参考。Self-Refine 是"当场改"，Reflexion 是"记错题本，下次先翻笔记"。

LATS

把 MCTS（蒙特卡洛树搜索）和反思结合：多路径探索 + 每条路径执行后反思 + 反思结果反馈给后续探索。既有规划的多路径又有反思的学习能力，代价极大，学术阶段。

辩论式反思

多个 Agent 互相辩论。正方提出方案，反方专门挑毛病、提反对意见，正方再针对反对意见优化。对抗式反思比单方面审查更能暴露深层问题。适用于商业决策分析、法律文本审查等高质量场景。

工程权衡

防死循环：必须硬性设置最大轮次（通常 2~3 轮），绝对不能依赖 LLM 自己判断停止。LLM 会陷入"为了改而改"的循环，每轮改动很小但无实质进步。3 轮反思 = 额外 6 次 LLM 调用，延迟和成本大幅增加。
LAYER 03

工程化任务拆解

把规划/反思能力落地到具体执行——怎么切大任务、怎么并行跑、怎么动态调整。

为什么任务要拆分？

根本原因：Context Window 有限。任务越大，中间状态越多，"桌面越乱"——搜索结果、分析意见、写了一半的段落堆在一起，LLM 很难持续追踪"我现在在做哪个子目标"。

拆分的好处：

  1. 每步聚焦一件事，LLM 全部注意力集中，桌面保持干净，质量自然高
  2. 每步是独立输出，可以被单独检查和验证，某步出错只需重试那一步

两种拆分思路

维度静态拆分动态拆分
谁来做人提前写死步骤流程LLM 根据目标自己规划
类比固定流水线项目经理做计划
优势行为完全可预测，出了问题好定位灵活性强，适应不同任务特点
劣势灵活性低，遇到没设计的流程就卡住规划质量不稳定，错了全错
本质固定 WorkflowPlan-and-Execute 模式
注意区分：CoT/ToT 是"LLM 内部怎么把一个问题想清楚"的推理方法（一次生成里的内部拆分），静态/动态拆分是"Agent 怎么把一个大任务切成多个独立执行的步骤"（涉及多步工具调用）。两者粒度和目标不同，不要混为一谈。

Plan-and-Execute 的三阶段落地

  1. 规划阶段（项目启动会）：把目标告诉 LLM，输出有序步骤列表。只做规划不执行，全部注意力集中在"想清楚要做什么"。
  2. 执行阶段（各部门干活）：逐步执行，每步把前面结果作为 context 传入，LLM 始终知道进度，不会"失忆"。
  3. 汇总阶段（项目验收）：所有步骤跑完后整合产出，解决各步骤衔接问题，确保最终输出连贯而非生硬拼接。

并行优化：依赖分析与 DAG

拆好步骤后，分析步骤间的依赖关系——有些必须等前一步完成，有些可以同时进行。识别可并行的步骤是降低总耗时的关键。

厨师类比：烧水、切菜、腌肉三件事，傻傻串行 = 三件事时间之和。有经验的厨师先烧水，同时切菜腌肉，总时间由最长路径决定。

# 依赖图：步骤 1 和 2 独立可并行，步骤 3 依赖 1，步骤 4 依赖 2 和 3
#
# 步骤1 ──────────────┐
#                      ├──> 步骤3 ──┐
# 步骤2 ──────────────┘             ├──> 步骤4（最终输出）
#          └──────────────────────  ┘
#
# 串行：4步 × 3秒 = 12秒
# 并行：max(步骤1,步骤2) + 步骤3 + 步骤4 = 3+3+3 = 9秒

import asyncio

async def execute_parallel_steps(independent_steps: list):
    tasks = [execute_step_async(step) for step in independent_steps]
    results = await asyncio.gather(*tasks)
    return results
实际收益：前提是依赖关系稀疏、工具 I/O 占主要耗时。如果所有步骤都强依赖上一步，并行空间为零。实践中降低 40%~60% 端到端延迟很常见。

拆分粒度的把握

粒度代价
太细调用次数多、token 上升；步骤太碎，LLM 看不到全局，衔接生硬
太粗每步负责的事太多，出错概率上升，出问题无法定位
原子操作只做一件独立的事，边界清晰，做完有明确输出，不依赖其他步骤

判断方法：能给它写一个清晰的函数签名吗？能 = 大概是原子的。如果函数里还要分好几个阶段 = 需要再拆。

自适应拆分：做不好就继续拆

不要在开始时就把所有步骤粒度定死，而是在执行过程中根据实际难度动态调整：

  1. 先让执行器尝试完成当前任务
  2. 做得好 → 继续往下走，不做多余拆分
  3. 做不好（超过最大步数 / 质量不达标）→ 交给规划器进一步拆成更小子任务
  4. 对每个子任务重复同样的流程

特性：任务越复杂，递归拆分层数越深；任务越简单，可能一层都不拆。计算开销与任务实际难度成正比，而非一刀切。

执行中的 Replan 机制

每步执行完后，把当前结果和剩余计划交给规划模块，判断"基于新信息，后面的计划还合理吗"。合理则继续，不合理则生成新的剩余步骤。

折中做法：不是每步都触发 Replan，而是设触发条件——当某步输出与预期差异很大时、或步骤执行失败时才启动。既能应对意外，又不会无谓增加消耗。

拆分结果的验证标准

标准含义检查方法
完备性所有步骤加在一起能覆盖原始任务的全部要求把步骤描述拼在一起，和原始任务逐项对照，看有没有遗漏
独立性每个步骤职责边界清晰，没有两个步骤做同一件事检查是否有输出重叠；如"搜索功能"和"分析能力"边界模糊需合并
可验证性每步执行完能用简单标准判断做对了没拆分时同时写好"验收标准"，像写单元测试断言一样
最佳实践：步骤定义和验收标准成对出现。例如步骤"搜索竞品 A 的定价信息"，验收标准 = "输出中必须包含价格数字和计费模式（按量/包月/免费增值）"。执行完自动检查，缺了就触发重试。
