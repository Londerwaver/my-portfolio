01

为什么需要 Multi-Agent

WHY MULTI-AGENT — 两个结构性硬限制驱动

单 Agent 的两大硬限制

Multi-Agent 的价值不是「多几个 AI 而已」，而是被两个很具体的工程问题逼出来的。 面试时能说出这两个结构性限制，就赢了大多数只会说「任务太复杂」的人。

限制一 · Context Window 的硬上限

LLM 处理任务，等于把「你的指令 + 它的推理过程 + 工具返回结果 + 历史对话」全部摆在 一张工作台上一起处理。这张工作台叫 context window，常见上限从 12.8 万到 100 万 token 不等。

桌子放满了，新的放进来，旧的就得被推到地上——早期确认的方案、第一批搜集的资料悄悄「掉落」， Agent 开始遗忘。这是结构性的上限，不是靠优化提示词能绕过去的。

核心结论
context 溢出导致「遗忘」是第一个硬限制：复杂任务的信息量一旦超出窗口，单 Agent 无解。
限制二 · 专业度：单点泛才问题

让一个 Agent 既搜信息、又写代码、又做测试、又写文档——它每件事都得兼顾，精力分散。 就像一个人同时担任产品经理、程序员、测试工程师和文档工程师，每个角色都做得不够专注。

而且一旦某个环节出问题，整条链路就卡住，没有隔离性，排查起来很痛苦。 分工之后，每个 Agent 的 context 是干净的，只装自己那块信息，专业能力也更强。

单打独斗 vs 团队作战：以「爬虫工具」为例

不用 Multi-Agent

一个 Agent 同时在想需求文档、代码结构、测试策略，context 塞满各种信息，思路乱成一锅粥， 写出来的东西哪块都不够好，而且任何一步失误都得从头来。

用了 Multi-Agent
  • 需求分析师：只做一件事，把用户需求转成清晰的功能列表，输出后即退出，工作台干净；
  • 程序员：拿到功能列表专注写代码，不需要知道需求怎么来的，context 里只有代码信息；
  • 测试工程师：拿到代码专注写测试用例……每个 Agent 的工作台都干净，专业度更高。
隐藏收益
需求分析结束后，程序员与测试其实可以并行开工（测试框架搭建不需要等代码写完）—— 这就是「并行扇出」：Orchestrator 识别无依赖的子任务同时派出，等全部结果回来再整合。 并行不只提速，还让每个 Worker 的 context 完全隔离，输出质量更高。

组织方式与框架生态

Multi-Agent 系统的组织方式主要有两种：

  • 中心化：由一个统一调度者分配任务、收集结果；工程上更常用——调度逻辑清晰、责任归属明确、容易排查。
  • 去中心化：Agent 之间自行协商、直接通信；听起来灵活，但工程问题很多（第二章详述）。

02

架构选型设计

SINGLE VS MULTI — 什么时候上，怎么组织

Single-Agent 的本质与边界

Single-Agent = 一个 LLM + 一套工具，跑一个决策循环：LLM 判断下一步做什么 → 调用工具执行 → 拿结果再判断 → 直到任务完成。

它的优势不只是「架构简单」

更核心的是整条任务链路完全在你掌控之内：任务怎么走、用什么工具、何时结束，所有逻辑在一个地方写清楚， 出问题链路短、好排查。类比一个人独立写一篇博客，自己查资料、想大纲、写下来，沟通成本为零，反而更高效。

三类信号：必须上 Multi-Agent
  1. 任务太长、信息量太大：context 撑爆，Agent 开始遗忘；
  2. 需要多种专业能力：什么都塞进一个 Agent，每件事都做得不够专注；
  3. 存在可并行的独立子任务：单 Agent 只能一个个来，理论上可并行却无法并行。
反过来也成立：不在这三类里，Single-Agent 就够了。不要为了「用新技术」强行上 Multi-Agent——系统变复杂、难维护，却带不来对应收益。

中心化方案：Orchestrator 模式

「Orchestrator」直译是交响乐指挥，在系统里相当于总调度员 / 项目经理。 它是整个系统里最特殊的 Agent——不做任何具体工作，只负责三件事：

  1. 读懂用户的大目标，把它拆成一个个子任务；
  2. 判断每个子任务该交给哪个 Worker Agent 去做；
  3. 收集每个 Worker 的产出，拼成最终答案。

Orchestrator 的三种变体（按复杂度递进）

变体机制适用场景

Worker Agent：纯粹的「执行者」

每个 Worker 只关注自己那块，不需要知道整体任务、不需要知道其他 Worker 在做什么； 拿到属于自己那部分指令，做完返回结果就退出。它的 context 干净，只装与自身职责相关的信息。

去中心化方案：为什么「听起来灵活」却几乎没人用

去中心化的思路是没有总调度，多个 Agent 通过共享的消息队列或状态空间自行协商、直接通信。 听起来像一个能自我组织的团队，不需要领导，还更灵活——但工程上几乎不用。

用具体场景暴露问题：A 搜信息、B 搜类似信息、C 汇总，没人统筹
  • 任务分配没有协调：没人告诉 A 和 B「各搜什么范围」，很可能大量搜索内容重叠，做重复工作；
  • 执行顺序没有保证：C 需要等 A、B 都搜完才能汇总，但没人告诉它「什么时候算搜完了」，该等多久、有没有漏掉谁都不知道；
  • 失败没有感知：A 中途出错，没有中央调度者收到通知，B、C 照常运行，最后汇总出的是不完整结果，系统甚至不知道出了问题。
本质问题
任务分配没协调、执行顺序没保证、失败没感知、没人确认「整体完成了」。 类比没有项目经理的团队：每个人都很能干，但没人协调时间节点和接口，交出来的可能是互不兼容的结果。

所以去中心化更多停留在学术研究（研究「AI 能否实现自主协调」这个更宏观的问题）； 生产环境里几乎所有正经项目都选 Orchestrator 模式——可控、可追踪、能排查，这才是工程真正需要的。

选型决策框架

两个问题搞定选型
  1. 你的任务，Single-Agent 能搞定吗？
    流程明确、不太长、不需要多种专业分工 → 就用 Single-Agent。架构简单、维护成本低、链路透明，别为了「显得高级」而复杂化。
  2. 你能接受系统行为不可控的风险吗？
    生产环境答案几乎一定是「不能」→ 用 Orchestrator 中心化模式。
渐进式演进（最实用的工程策略）
先用 Single-Agent 把系统跑起来，等发现某个环节确实成为瓶颈（context 常撑满、某类子任务质量不行）， 再把那个环节拆出来交给专门的 Worker。不要一上来就设计五六个 Agent 的系统——你可能连真正的瓶颈在哪儿都还没搞清楚。 Single → Multi 是一个自然演进，而不是一开始就做的架构决策。

行业趋势：A2A 协议（Agent-to-Agent）

Google 于 2025 年 4 月提出的开放标准，解决不同团队、不同框架开发的 Agent 之间如何互相通信协作的问题。 思路很像微服务：定义一套标准化通信协议，让不同来源的 Agent 在协议层面互相发现与调用。 2025 年 6 月已捐给 Linux 基金会维护，IBM 的 ACP 协议也已并入。 目前仍在早期阶段，「跨框架即插即用」尚未成熟，多为社区实现与示范项目——但长远看会深刻改变 Multi-Agent 的构建方式。

03

协作与动态切换机制

COLLABORATION & ROUTING — 信息怎么传、下一步叫谁

三种协作模式总览

  • 流水线模式：Agent 按固定顺序依次执行，前一个完成后交给下一个，像工厂装配线；
  • 层级模式：Orchestrator 负责分配任务、收集结果，其他 Agent 各自执行子任务；
  • 协商模式：多个 Agent 之间没有严格上下级，通过互相沟通、辩论达成一致。
三种模式不是互斥的，复杂系统里经常混合使用。

通信方式：消息传递 vs 共享状态

把多 Agent 系统想象成公司的多个部门：研究部、开发部、测试部各司其职。部门之间传信息，有两种方式。

📧 消息传递 · 像发邮件

Agent 完成工作后把结果发送到消息队列，下游 Agent 订阅感兴趣的消息，取到了再开始处理。

优点：解耦——发送方不需要知道谁在接收，只管发；接收方也不需要知道消息是谁发的，只管处理。

缺点：需要「邮件服务器」（消息中间件）维护这套机制，部署成本稍高。

📋 共享状态 · 像共享白板

所有 Agent 都读写同一个状态对象，上面记录「当前任务、进展到哪、各部门完成了什么」。

Shared State（LangGraph 的 State）
研究部资料整理完成 ✓
开发部代码开发中…
测试部等待中

研究部写上「资料整理完成」，开发部一看知道可以开始了，接手写「代码开发中」。

代表：LangGraph 就按这个思路设计——贯穿所有 Agent 的 State，执行完写入结果，下一个直接读取。

怎么选
Agent 之间依赖关系强（前一步结果直接传给后一步）→ 用共享状态，直接；想让 Agent 尽量解耦、互不知道对方存在 → 用消息传递。

共享状态设计要点

多个 Agent 同时读写一个状态对象，是系统里最容易出 bug 的地方——写的结果被意外覆盖、读到一半更新的脏数据，都会出问题。工程上有三个关键点。

① 状态分层
  • 全局状态：所有 Agent 都要读的信息——用户原始请求、任务进展、最终输出，共享；
  • 局部状态：每个 Agent 自己的中间结果——搜索候选列表、代码草稿，只在内部使用，不暴露给其他 Agent，避免信息污染。
② 只追加，不覆盖

每个 Agent 完成后把结果追加到状态里，而不是修改已有字段。LangGraph 的 State 更新就是这个思路： 定义好 schema，每个节点返回「增量更新」，框架帮你合并进全局状态，就不会互相覆盖。

③ 错误也要写入状态

Agent 执行失败，错误信息也应写入状态，不能悄悄吞掉。后续 Agent 或 Orchestrator 读到错误状态， 才能正确决策：跳过这一步、换 Agent 重试、或直接终止任务。

路由策略：静态路由 vs 动态路由

「切换」= 决定下一步把任务交给哪个 Agent，这个决策动作叫路由，由 Orchestrator 负责。

📐 静态路由 Static

把规则提前写死：任务描述含「搜索」→ Researcher；当前步骤「代码写完了」→ Reviewer；匹配不到 → 回 Orchestrator 兜底。

✅ 优点
  • 效率高、可预测、好调试
  • 像工厂流水线，每道工序后去哪个工位是固定的
⚠️ 缺点
  • 覆盖不了没预料到的情况——任务走了没定义规则的路径，系统就不知怎么办
稳定欠灵活
🧠 动态路由 Dynamic

把「下一步找谁」交给 LLM 决策：Orchestrator 把当前任务描述、已完成进度、可用 Agent 列表全部喂给 LLM，让它判断该叫谁。

✅ 优点
  • 能处理任何没预先设计的路径，边缘情况也能合理判断
⚠️ 缺点
  • 每次路由多一次 LLM 调用：延迟 + 成本
  • LLM 偶尔路由错，行为可预测性降低
灵活延迟/不可控

动态路由的代码实现（简化示例）

dynamic_route.py 
def dynamic_route(task_context: str, available_agents: list[str]) -> str:
    """让 LLM 根据当前上下文决定下一步调用哪个 Agent"""
    prompt = f"""当前任务状态：
{task_context}

可用的 Agent：
{chr(10).join(f'- {agent}' for agent in available_agents)}

请根据当前进展，判断下一步应该交给哪个 Agent 来执行。
只返回 Agent 名称，不需要解释。"""

    response = client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )
    selected = response.choices[0].message.content.strip()
    return selected  # 返回选中的 Agent 名称
生产环境通常还会加保护措施：校验返回的 Agent 名是否在可用列表中、设置默认 fallback Agent、记录路由决策日志供后续分析。

Handoff 模式：Agent 之间的「接力棒」

比中央 Orchestrator 更去中心化的一种切换方式，由 OpenAI 的 Swarm 框架演示推广 （Swarm 是教育性/实验性框架，官方明确非生产级，但对概念展示非常直观）。

Handoff 的思路：不需要中央调度，当前正在执行的 Agent 自己决定「我做完了，接下来交给谁」。 像接力赛跑，每个运动员跑完自己那棒，直接把接力棒递给下一个人，不需要裁判喊「下一个是谁」。

优缺点对比
  • 优点：每个 Agent 对自己的任务边界最清楚，由它决定下一步找谁，往往比外部 Orchestrator 判断更准确；没有中央节点瓶颈，扩展性好。
  • 缺点：没有全局视角——A 交给 B，B 觉得不是自己的活又交给 C，C 又交回给 A，就形成死循环。
使用前提
必须设计好每个 Agent 的职责边界，并加防循环机制：记录任务经过哪些 Agent，发现重复经过同一 Agent 就强制终止。

工程实践：组合拳

最稳健的做法
  • 主流程用静态路由：把确定性的节点切换写成规则，保证绝大多数情况下系统行为稳定可预测；
  • 边缘情况交给 LLM 动态决策：遇到没有匹配规则的路径，才让 LLM 判断；
  • 一句话：静态路由负责「保底」，动态路由负责「兜住异常」，两者互补。
Handoff 与通信方式怎么选
  • Handoff：适合 Agent 数量不多、职责边界清晰、任务流向相对确定的场景，比中央 Orchestrator 更简洁；Agent 多、流向复杂，还是建议 Orchestrator 统一调度，避免交接变成一团乱麻。
  • 通信方式：流程是相对清晰的流水线、各步骤有明确前后依赖 → 共享状态（简单直接）；需要多个 Agent 独立并行、互相不感知 → 消息传递（解耦清晰）。

面试要点速记

INTERVIEW CHEATSHEET — 三个最容易踩的雷

🧭答题要讲设计取舍，不要停在表面

1

选型标准不能说「任务复杂就用 Multi-Agent」，要说具体场景。

✅ 正确答法：context 要撑爆、需要不同专业分工、有子任务可并行，三类信号都不占就用 Single-Agent；盲目引入只会增加复杂度，带不来收益。
2

回答 Multi-Agent 架构，要主动提中心化 + 去中心化两种，并给出明确取舍。

✅ 正确答法：工程里几乎都选 Orchestrator 中心化模式，因为可控、可追踪、能顺着调度链路排查；去中心化「听起来灵活」但有实际问题。
3

去中心化要说清楚它为什么在工程上不可用，而不是「更灵活」。三个具体问题：

✅ 任务分配没协调、执行顺序没保证、失败没有感知——这才是它停留在学术研究的根本原因。
4

协作机制要说出两种通信方式的本质区别。

✅ 消息传递的核心是解耦（发送方不知道谁在接收，适合独立并行）；共享状态的核心是直接（所有 Agent 读写同一对象，LangGraph 就是这个思路，适合依赖明确的流水线）。选哪个看依赖强度。
5

动态切换要说出静态 / 动态路由各自的优缺点，以及最体现工程经验的那句混用策略。

✅ 「主流程静态路由保底，边缘情况才交给 LLM 动态决策」——面试官一听就知道你真的做过多 Agent 系统。
