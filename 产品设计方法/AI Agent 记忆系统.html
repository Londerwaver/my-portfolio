Agent 记忆系统 STUDY NOTE
记忆全景

为什么 Agent
需要记忆？

一个没有记忆的 Agent，每次对话都是全新的开始——昨天确认的偏好、达成的约定、执行到一半的任务状态，全部消失。记忆系统解决两件事：一次任务内保持状态，跨任务积累知识。

一、没有记忆的 Agent 有多惨
两个核心能力直接缺失
🧠
无法跨任务积累知识
你今天说「代码风格简洁、变量用英文命名」，明天它就给你输出中文变量名、啰嗦注释的代码。每次都从零开始，永远无法「越来越了解你」。

类比：每次看病的医生都不记得你的病史，每次都要重新问一遍。
📋
无法在多步任务中保持连贯
多步任务中，它不知道自己做到哪了、前面收集了什么信息。「先查资料再整理报告」这种任务根本无法执行——第二步忘了第一步的结果。

类比：厨师做菜做到一半失忆，不记得自己放了什么调料、菜炒到几成熟。

「记忆系统解决两件事——一次任务内保持状态（知道做到哪了），跨任务积累知识（越来越了解用户）。这两件事分别由短期记忆和长期记忆承担。」

— 记忆系统核心定义
二、四种记忆类型：从最短暂到最持久
借用人脑的记忆层次模型
人脑类比
人脑有「感觉记忆」（几秒）→「短期记忆」（几分钟到几小时）→「长期记忆」（数年到终身）。Agent 的记忆层次与此对应，但多了一层「实体记忆」——从对话中提炼出的结构化事实，信息密度最高、查询最快，相当于医生的病历卡。
感知记忆
当前这次调用的原始输入——用户消息、上传截图、传入文档。处理完就消失，生命周期只有一次调用。相当于人「刚听到还没记住」的那几秒。
↓
短期记忆
context window 里的 messages 列表，维持当前任务的完整状态。任务结束就清空。相当于「工作台」，桌面摆着正在处理的东西，有大小限制。
↓
长期记忆
存在外部数据库（向量/关系/KV），跨任务持久化。需要时主动检索拿回来。相当于「档案室」，东西不会丢，但要用得主动去翻。
↓
实体记忆
从对话中提炼出的结构化事实——「用户偏好 Python」「预算 5 万」「截止日 3 月底」。信息密度最高，查询最快。相当于医生的病历卡。
类型 载体 容量 生命周期 访问方式
感知记忆 当次输入 极小 单次调用 即时访问
短期记忆 context window 受 token 限制 一次任务 直接读取
长期记忆 向量 / 关系数据库 无限 持久 语义检索
实体记忆 结构化存储 无限 持久 精确查询

短期记忆

Agent 的
工作台

短期记忆就是每次调 LLM 时传入的 messages 列表，维持当前任务的完整状态。每一步产生的内容都追加进去，任务结束清空。它的核心瓶颈是 context window 有大小限制。

一、基本实现：messages 列表
每条消息有 role 和 content

每条消息有 role（user / assistant / tool）和 content。每一步产生的内容都追加进去，每次调 LLM 传完整历史，任务结束清空。

class ShortTermMemory: def __init__(self): self.messages = [] def add(self, role: str, content: str): self.messages.append({"role": role, "content": content}) def get_context(self): return self.messages # 每次调 LLM 传完整历史 def clear(self): self.messages = [] # 任务结束清空

「每次调用都传完整历史 → messages 越来越长 → context window 装满 → 早期内容被截断 → Agent 开始『遗忘』。这是短期记忆的天然瓶颈，也是记忆压缩策略存在的根本原因。」

— 短期记忆核心代价
二、进阶：结构化工作记忆
给「工作台」划分固定区域
为什么需要结构化
纯粹的 messages 列表什么都往里塞，比较粗放。结构化工作记忆的思路是给「工作台」划分固定区域：当前任务目标、已确认的中间结论、待验证的假设分别存放，主动更新而非简单追加。即使对话很长，工作台始终结构清晰，LLM 每次读到的都是当前最准确的任务状态。
①
区域 01
当前任务目标
正在做什么、目标是什么。任务执行过程中可能动态调整——用户追加了新需求，或者发现原目标需要修正。
关键：不是追加新目标，而是更新目标区，确保 LLM 始终看到最新目标。
②
区域 02
已确认的中间结论
已经确定的事实和决策。比如「用户确认用 Flask 框架」「数据库选 PostgreSQL」。这些是后续推理的已知条件。
关键：结论确认后从「假设区」移到「结论区」，状态更新而非堆积。
③
区域 03
待验证的假设
还没确认的猜测，需进一步验证。比如「猜测用户需要 SSR 支持，但还没确认」。验证后移入结论区或删除。
关键：区分确定和不确定的信息，避免 LLM 把假设当事实用。
④
区域 04
动态更新机制
核心区别：不是只追加，而是主动替换过时内容。新结论覆盖旧假设，任务目标更新时旧目标被替换。
关键：工作台保持精简，只反映当前最新状态，不是历史堆积。
三、短期记忆 vs 长期记忆：作用时机
面试最常考的对比
短期记忆
执行中的工作台 任务执行过程中全程工作。每一步结果追加进 messages，LLM 每次调用读取完整历史来保持上下文连贯。任务结束即清空。
vs
长期记忆
任务前检索 + 任务后写入 任务开始前：用任务描述检索相关记忆，注入 system prompt。任务结束后：把重要结论写入长期记忆沉淀。执行中不直接参与，除非主动检索。

「短期记忆是执行中的工作台，长期记忆是任务前的背景知识和任务后的知识沉淀。搞混这两者的作用时机，是面试中最常见的错误。」

— 两层记忆作用时机（面试雷区）
来源：第 9 篇
长期记忆

Embedding + 向量数据库，
语义检索的档案室

长期记忆的核心是 Embedding + 向量数据库，靠语义相似度而非关键词匹配来召回记忆。它还细分为情节、语义、程序三种子类型，各有不同价值。记忆粒度和衰减机制是工程设计中最关键的决策。

一、两个核心概念
Embedding 和向量数据库
RGB 颜色类比
Embedding 把文字转成几百到几千维的浮点数向量，捕捉文字的「语义」。语义相近的文字，向量在空间里距离也近。类比 RGB 颜色编码——红色 (255,0,0) 和橙色 (255,165,0) 数值近，因为颜色相近；红色和蓝色 (0,0,255) 数值远，因为颜色不相近。Embedding 做的就是把「语义」编码成数值，让相似性可计算。
🔢
Embedding：文字 → 数字向量
把文字输入 Embedding 模型（如 OpenAI 的 text-embedding-3-small），输出一个固定维度的浮点数向量。这个向量编码了文字的语义信息。

关键：不是关键词匹配，而是语义理解。「如何部署网站」和「怎么上线网页」用词不同但语义相近，向量距离也近。
🗄️
向量数据库：相似度检索引擎
专门存向量的数据库（如 ChromaDB、Pinecone、Weaviate），核心能力是「相似度检索」：给一个查询向量，找库里距离最近的几条记录。

关键：用 HNSW / IVF 等 ANN 索引加速，不用逐条比对。类比图书馆索引卡，不用逐本翻就能定位。
🔄
存取流程
存入：内容 → Embedding 向量 + 原文 + metadata → 写入向量数据库。

检索：查询 → Embedding 向量 → 找向量距离最近的 N 条 → 返回原文。

关键：存的不只是向量，还有原文和元信息（时间、类型、重要程度）。
from openai import OpenAI import chromadb client = OpenAI() db = chromadb.Client() collection = db.get_or_create_collection("agent_memory") def save_to_long_term(content: str, metadata: dict): # 1. 文字 → 向量 embedding = client.embeddings.create( input=content, model="text-embedding-3-small" ).data[0].embedding # 2. 向量 + 原文 + 元信息 一起存 collection.add( embeddings=[embedding], documents=[content], metadatas=[metadata], ids=[f"mem_{hash(content)}"] ) def retrieve_memory(query: str, top_k=3): # 1. 查询 → 向量 q_emb = client.embeddings.create( input=query, model="text-embedding-3-small" ).data[0].embedding # 2. 找向量距离最近的几条 results = collection.query(query_embeddings=[q_emb], n_results=top_k) return results["documents"][0]
二、长期记忆的三种子类型
情节、语义、程序——三者混合使用效果最好
情
Episodic · 情节记忆
具体事件经历
存「发生了什么」。记录具体的交互事件和解决过程。例：「上周二写爬虫遇到反爬，用 Selenium 解决了」。
价值：遇到类似任务时参考上次怎么解决的，不需要从零摸索。
语
Semantic · 语义记忆
从经历提炼的通用知识
存「总结出什么」。从多次经历中抽象出的一般规律。例：「目标网站有 JS 动态渲染时，requests 抓不到，用 Selenium/Playwright」。
价值：信息密度高，更容易命中。是情节记忆「蒸馏」后的产物。
程
Procedural · 程序记忆
操作流程 / SOP
存「怎么做」。标准化的操作步骤。例：「部署 Flask：虚拟环境 → 装依赖 → gunicorn → nginx」。
价值：重复性任务直接复用流程，不需要重新推理，响应最快。
合
三者配合
混合使用效果最好
情节记忆提供参考案例 → 语义记忆提供抽象规律 → 程序记忆提供可复用流程。三者形成从具体到抽象的完整知识体系。
关键：记忆整合的核心工作就是把情节记忆「蒸馏」成语义记忆。
三、记忆粒度：存多细才合适
最容易踩坑的设计决策
粒度太细 ❌
每句话存一条
把「用户偏好 Python，不喜欢全局变量，风格追求简洁，注释用英文」拆成四条存。

结果：检索时可能只命中其中两条，记忆碎片化，LLM 拿到不完整的偏好信息。
vs
粒度太粗 ❌
整次对话存一条
把一整次 2000 token 的完整对话存成一条。

结果：检索命中了，但 2000 token 里真正相关的可能只有 100 个，LLM 被无关内容干扰。

「合理粒度——以『一次完整交互』或『一个独立知识点/事件』为单位存储。前者保证信息完整性（用户请求 + 处理结果），后者把偏好打包成一条结构化记录，检索时一次拿到完整信息。过程中的细小中间结果不需要存长期记忆，短期记忆够用。」

— 记忆粒度设计原则
四、记忆衰减与记忆整合
记忆不是只增不减，需要主动维护
为什么需要衰减
人的记忆会随时间淡化，Agent 的长期记忆也应该有类似机制。用户半年前说「我在学 Go」，但最近三个月都在聊 Python，如果不做衰减，Agent 还按「用户在学 Go」处理就很违和。记忆用久了还会积累大量碎片——同一主题存了十几条，重复、过时、矛盾。记忆整合就是定期做「清理和升华」。
⏳
记忆衰减
新鲜度权重：给每条记忆加时间权重，检索排序时同时考虑语义相似度 + 时间新鲜度，越久远权重越低。

定期审查：让 LLM 定期审查长期记忆库，标记过时/矛盾的记忆为失效或合并更新。
🔀
去重
语义相近的多条合并成一条更完整的版本。「喜欢简洁代码」+「代码要精简」+「不要冗余代码」→ 合成一条。

关键：不是文本相同才去重，是语义相近就去重，需要 LLM 辅助判断。
⚖️
冲突消解
两条矛盾时（「偏好 Python」vs「最近转用 Go」），保留时间更新的，标记旧的为过期。

关键：时间戳是冲突消解的核心依据。没有时间戳就无法判断哪条更新。
💎
抽象提炼（最有价值）
把多条情节记忆「蒸馏」成一条语义记忆。三次爬虫经历 → 「动态渲染网站用浏览器自动化工具」。用 LLM 自动完成。

价值最大：这是记忆系统真正变「聪明」的关键——从具体经验中提炼通用规律。
📅
整合节奏
轻量更新：每次任务后做去重和冲突检查。

深度整理：每天/每周做一次抽象提炼。Mem0 等框架已内置异步整合能力。
　
　
　
来源：第 8 篇、第 9 篇
记忆压缩

context window 快满了，
怎么办？

短期记忆有 context window 硬上限，压缩是刚需；长期记忆虽无硬上限，但记忆膨胀会导致检索质量退化，同样需要整合与衰减。四种压缩方法解决短期「装不下」，粒度选择/去重/冲突消解/抽象提炼/衰减解决长期「检索变差」。两层压缩不是割裂的，而是连通的管道。

一、四种压缩方法
从不同维度解决空间问题
①
时间维度 · 直接截
滑动窗口
只保留最近 N 轮对话，更早的直接丢弃。最简单的方法，但「硬截断」——关键决策和闲聊被同等对待。
优点：零开销，实现极简
缺点：重要信息可能被丢掉
②
时间维度 · 截前提炼
摘要压缩
丢弃前先让 LLM 把历史总结成摘要，用摘要替换原文。进阶：层级式摘要——近期保持原文，中期做摘要，远期做更精炼摘要。
优点：保留关键信息脉络
缺点：摘要丢失细节，有额外 LLM 调用开销
③
价值维度
重要性过滤
不按时间，按价值筛选。给每条记录打重要性分数（规则打分或 LLM 打分），低于阈值淘汰。进阶：观察遮蔽——不删，按任务阶段选择性隐藏。
优点：打破时间顺序，保留高价值内容
缺点：打分有成本，规则打分不够精准
④
载体维度
结构化抽取
换载体——不存对话文本，把关键事实提取成结构化字段。「偏好 Python」「预算 5 万」「已确认方案 B」，直接存字段。
优点：信息损失最小，密度最高
缺点：开发成本最高，需预定义字段，通用性低

「四种方法不互斥，可以组合使用。最常见的工程组合是滑动窗口 + 摘要压缩——近期保持原文，中期用摘要替代，远期直接截断。」

— 压缩方法组合策略
二、四种方法对比
解决的问题维度不同
维度 方法 解决的问题 信息损失 实现成本
时间 · 直接截 滑动窗口 历史太长，直接截断 高（硬截断） 最低
时间 · 截前提炼 摘要压缩 截之前先保留关键信息 中（摘要丢细节） 中
价值维度 重要性过滤 内容不等价，按价值筛选 低（保留高价值） 中高
载体维度 结构化抽取 对话文本不是最佳载体，换高密度形式 最低 最高
三、主动压缩 (Proactive Compression)
不等快满才压缩
核心思路
不等 context 快满才压缩，而是每步执行后主动判断哪些中间过程可以压缩。比如工具返回 2000 token 的搜索结果，Agent 读完立刻压缩成 200 token 要点替换原始内容。适合工具调用频繁的 Agent——每次工具返回都可能是大块文本，不主动压缩很快就会爆 context。
被动压缩
等快满了再压 一次性对大段历史做摘要或截断。压力大、信息损失集中、可能来不及。
vs
主动压缩
每步即时压缩 工具返回后立刻提炼要点替换原文。压力分散、信息损失分散、context 始终保持精简。
四、Prompt Caching：计算层优化
与记忆压缩互补，不是替代
信息层 vs 计算层

六、短期 vs 长期：压缩的两个战场
压缩不只是短期记忆的事
核心澄清
很多人以为压缩只是短期记忆的刚需——毕竟 context window 有硬上限。但长期记忆（向量数据库 / 结构化数据）同样需要压缩，只是形式不同、目的不同、触发时机不同。短期压缩解决「装不下」，长期压缩解决「检索变差」。两者不是割裂的，而是连通的管道。
短期记忆压缩
解决「装不下」 载体是 messages 列表，有 硬性 token 上限（context window）。压缩是刚需：滑动窗口砍历史、摘要压缩保留脉络、重要性过滤按价值筛、结构化抽取换高密度载体。压缩是实时执行，对话过程中就要做。
vs
长期记忆压缩
解决「检索变差」 载体是向量数据库，没有 context window 那种硬上限。但记忆无限膨胀会导致检索质量退化（相似度噪声增大、召回准确率下降）+ 存储成本上升 + 旧信息干扰新决策。压缩是定期批量执行，任务后或定时审查。
长期记忆的四种「压缩」手段
不是滑动窗口和摘要，而是整合与维护
📦
粒度选择
存的时候不存每句话、也不存整次对话，以「一次完整交互」或「一个独立知识点」为单位。粒度决策本身就是压缩——在写入阶段就决定了存多少、丢多少。
🔀
去重
语义相近的多条合并成一条。「喜欢简洁代码」+「代码要精简」+「不要冗余」→ 合成一条。信息压缩，减少冗余存储。
⚖️
冲突消解
两条矛盾时（「偏好 Python」vs「最近转用 Go」），保留更新的，标记旧的过期。质量压缩，消除噪音。
💎
抽象提炼
把多条情节记忆「蒸馏」成一条语义记忆。三次爬虫经历 → 「动态渲染网站用浏览器自动化工具」。语义压缩，从具体经验提炼通用规律。价值最大。
⏳
衰减（软删除）
给每条记忆加新鲜度权重，越久远权重越低，低到阈值就清理。相当于长期记忆的「滑动窗口」——不是硬删，而是渐隐。
　
　
　
维度 短期记忆压缩 长期记忆压缩
触发原因 context window 硬上限 检索质量退化 + 存储成本 + 信息过时
主要手段 滑动窗口、摘要、重要性过滤、结构化抽取 粒度选择、去重、冲突消解、抽象提炼、衰减
执行时机 实时（对话过程中） 定期批量（任务后 / 定时审查）
本质 在有限空间内最大化信息密度 在无限空间中保持信号纯度
如果不做 context 爆掉，Agent 崩溃 检索噪声大、召回不准、旧记忆干扰新决策

「两层压缩不是孤立的——当短期记忆通过摘要/结构化抽取压缩后，产出物会写入长期记忆；而从长期记忆检索回来的内容注入到短期记忆时，依然要占 context window 的空间。长期记忆压缩做得越好，注入短期记忆的信号质量越高、噪音越少。这是一个连通的管道。」

工程实践

从理论到落地：
三问 + 框架 + 闭环

工程实践的核心是回答三个问题：存什么、怎么存、什么时候取。此外，知识图谱让记忆产生关联，开源框架提供现成方案，读→用→写闭环把所有部分串在一起。

一、工程三问
存什么 / 怎么存 / 什么时候取
Q1
存什么
判断标准：下次有用吗？
这条信息，下次任务开始时如果知道，会让 Agent 做得更好吗？
✅ 值得存：用户偏好/习惯、关键结论/决策、外部知识
❌ 不值得存：中间推理过程、工具原始数据、闲聊
Q2
怎么存
根据类型选存储介质
不要一刀切，根据信息类型选存储介质。
非结构化文本（文档、摘要）→ 向量数据库
结构化偏好/状态 → 关系数据库 / KV 存储
主流做法 → 混合存储
🔍
Q3 · 主动检索（任务开始前）
任务开始前，用任务描述检索相关记忆，注入 system prompt 作为背景知识。Agent 一开始就带着「历史记忆」进入任务。

类比：医生看诊前先翻病历，带着病史进入这次问诊。
⚡
Q3 · 按需检索（执行过程中）
把「查记忆」封装成 Tool，Agent 在推理过程中自己判断什么时候调。更灵活，但依赖模型判断力。

类比：医生看诊中遇到不确定的症状，主动去查医学文献。

实践最佳：session 开始时主动检索加载背景，执行中按需检索专业知识。两者结合。

二、知识图谱：让记忆产生关联
向量数据库做不到的事
向量检索的盲区
存了「用户 A 是公司 B 的 CTO」和「公司 B 主营云计算」，问「用户 A 所在公司做什么业务」——纯向量检索找不到，因为这两条文本语义不相近。知识图谱解决的就是这个问题：用「实体 → 关系 → 实体」的三元组存储信息，查询时沿关系链条做多跳推理。

· ❌ 不擅长精确关系推理

精确关系推理
· ❌ 不擅长模糊语义匹配

— 知识图谱与向量数据库配合策略
实战案例：证据驱动的知识库治理
LLM 生成的知识，如何安全地写进知识图谱
核心问题
图谱里的三元组从哪来？最常见做法是让 LLM 从对话和文档里自动抽取实体与关系。但 LLM 会幻觉——可能抽错、可能编造、可能基于过时信息下结论。如果让 LLM 直接写图谱，一次幻觉就会污染整张图，且无法溯源。实战解法是四阶段机制：Evidence → Proposal → Decision → Identity——让 LLM 只当「参谋」，确定性系统当「法官」。
E
确定性来源
Evidence 证据
知识库的原始事实依据：代码调用关系、配置值、文档、运行数据。客观存在，可验证。
关键：不是 LLM 想出来的，是系统扫出来的。
P
LLM 输出
Proposal 候选提案
LLM 基于证据生成的知识建议（三元组）。可能看错、可能过时、可能混淆相似实体。
关键：默认不被信任，绝不能直接入库。
D
确定性门禁
Decision 决策校验
用代码逻辑而非 LLM 判断：比对证据是否真实存在、与 CurrentView 是否冲突、schema 是否合法。
关键：确定性——同一提案永远得到同一结论。
I
最终可信状态
Identity 发布身份
校验通过的提案原子化写入 Neo4j CurrentView，带 ID、时间戳、证据链接。
关键：随时能回答「这条知识是哪来的」。
# 四阶段流程（伪代码） # 1. 抽取证据（确定性） evidence = scan_code("orderService.submit() → paymentService.pay()") # 2. LLM 生成候选（可能出错） proposal = llm.extract_triples(evidence) # 建议新增一条边 # 3. 确定性门禁校验（不可跳过） if gate.verify(proposal, against=evidence) \ and not gate.conflict(proposal, CurrentView) \ and gate.schema_ok(proposal): pass else: discard(proposal) # 或补充证据后重新提案 # 4. 原子化发布（带身份） identity = CurrentView.commit(proposal) # 写库，可溯源

def run_agent_with_memory(user_request, long_term_memory, short_term_memory): # ── 读：任务开始前检索长期记忆 ── relevant = long_term_memory.retrieve(user_request, top_k=3) system_prompt = f"""你是一个智能助手。 以下是用户的相关历史信息，请在处理任务时参考： {chr(10).join(relevant)}""" short_term_memory.add("system", system_prompt) short_term_memory.add("user", user_request) # ── 用：执行任务，短期记忆维持状态 ── result = execute_task(short_term_memory) # ── 写：任务完成后，重要结论写入长期记忆 ── if result.is_important: long_term_memory.save( content=result.summary, metadata={"task_type": "coding", "timestamp": now()} ) short_term_memory.clear() # 清空，等待下一个任务 return result

「每次任务开始时把历史积累读进来，执行中靠短期记忆保持连贯，结束后把新知识写回去沉淀。Agent 用得越多，积累越厚，越来越『了解』用户——这才是记忆系统真正的价值。」

五、面试雷区速查
四个最常犯的错误
❌
雷区 1：长期记忆 = 关键词搜索
长期记忆说成「存数据库靠关键词搜索」→ 应该是 Embedding + 向量数据库，语义检索。关键词搜索找的是字面匹配，语义检索找的是意思相近。
❌
雷区 2：粒度越细越好
以为粒度越细越好 → 太细导致记忆碎片化，检索时只能命中碎片，LLM 拿到不完整信息。合理粒度是「完整交互」或「独立知识点」。
❌
雷区 3：只知道滑动窗口
记忆压缩只知道滑动窗口 → 实际有四种方法，解决不同维度的问题：时间维度（滑动窗口/摘要）、价值维度（重要性过滤）、载体维度（结构化抽取）。
❌
雷区 4：搞混两层记忆作用时机
搞不清两层记忆的作用时机 → 短期是执行中工作台，长期是任务前检索 + 任务后写入。不是两层记忆同时工作，而是各司其职、分阶段配合。
