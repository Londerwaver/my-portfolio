AI Native Requirement Operating System

AI Native 需求链路改造思考

从“人写需求、AI 辅助”升级为“业务意图进入系统后，AI 自动完成上下文理解、影响分析、规格生成、开发执行、语义校验和记忆回写，人只在高价值决策点介入”。

它不是把 PRD 写得更快，而是把需求变成可执行、可验证、可追溯的 Semantic Contract。

一、总体定位

新链路的目标不是再做一个“AI 写 PRD 工具”，而是建设一个 AI Native 需求操作系统。它以业务意图为入口，以企业记忆和代码图谱为上下文，以语义契约为中间锚点，最终把需求、开发、测试、评审、发布和记忆沉淀串成一个闭环。

输入

一句话需求 / 文档 / 会议 / 用户反馈

产品不再从空白 PRD 开始，而是从真实业务意图、用户问题或运营反馈开始。

中间

业务记忆 + 代码图谱 + Agent 协作 + 风险治理

AI 先理解上下文，再进行影响分析和规格生成，关键语义由人确认。

输出

可读需求、可执行规格、可开发任务、可验证测试

所有产物都围绕 Semantic Contract 展开，并在 merge 后回写企业记忆。

二、总链路

这条链路可以理解为四段：先把需求说清楚，再判断影响和风险，然后进入开发执行，最后用结果反哺企业记忆。

Phase 1

理解需求

接收一句话、文档、会议或反馈，先补上下文，再生成产品能确认的需求理解卡。

Phase 2

形成契约

明确影响范围、业务规则、验收条件和风险等级，形成 Semantic Contract。

Phase 3

执行开发

把契约转成开发包，交给 Agent 或研发执行，并在 MR 阶段校验是否兑现。

Phase 4

沉淀记忆

发布后结合测试、日志、指标和反馈，把业务事实、决策和证据回写企业记忆。

1

需求入口

产品不从空白 PRD 开始，而是从一句话、会议纪要、飞书文档、Jira、用户反馈或运营问题开始。

2

上下文组装

AI 先查业务记忆、代码图谱、历史需求、历史 MR、接口文档、测试用例、线上指标和事故记录。

3

需求澄清

AI 生成产品能看懂的需求理解卡：我理解的目标、当前假设、不确定问题、建议确认项。

4

影响分析

产品确认大方向后，系统分析可能影响的业务流程、系统、代码区域、状态、数据和外部依赖。

5

语义契约生成

把用户目标、业务规则、影响范围、非目标、验收条件、数据变化和风险统一成 Semantic Contract。

6

风险分级与审批

按风险决定 human out / on / in the loop：低风险自动推进，高风险必须审批。

7

开发包生成

生成 PRD 投影、OpenSpec、任务拆分、测试计划、代码影响清单、验收契约和风险说明。

8

Agent 开发

开发 Agent 拿到完整上下文包，自动建分支、改代码、补测试、跑验证、生成 MR。

9

MR 语义校验

MR 不只看 diff，还检查代码是否兑现语义契约，是否改了未声明的业务规则或影响额外范围。

10

发布验证

发布后看 CI、关键日志、业务指标、异常率、消息堆积、订单/权益一致性和用户反馈。

11

企业记忆回写

把需求、契约、代码变更、测试结果、决策记录、Agent trace 和发布观测沉淀为下一次可复用的证据。

例子：体验课用户转正式班时，自动处理原班级课程权益和赠课权益

这个例子不是在展示“查一次业务记忆、再查一次代码图谱、最后又写回一次”的重复动作，而是在展示一个飞轮：先读上下文，再对齐意图，然后精确分析，接着执行验证，最后写回记忆。

读上下文 对齐意图 精确分析 执行验证 写回记忆

1. 需求入口：先保存原始意图

产品输入一句话：“体验课用户转正式班时，需要自动处理原班级课程权益和赠课权益。”

系统不会立刻写 PRD 或派开发任务，而是先形成一条 RequirementEpisode：记录原始需求、来源、提出人、业务线、时间和上下文链接。这是后续所有判断的原始证据。

2. 上下文召回：不是做影响分析，而是避免裸聊需求

产品的一句话通常是模糊的。AI 需要先查业务记忆、代码图谱、历史需求、历史 MR、测试、事故和指标，弄清楚企业内部到底怎么称呼、怎么实现、以前怎么改过。

如果不查上下文，AI 不知道
  • 企业里这个业务叫“转班”还是“升班”
  • 已有流程是提交转班申请，还是直接执行转班
  • 赠课权益在哪个服务里处理
  • 历史上有没有类似需求或事故
  • 已有测试覆盖了哪些规则
这一步产出什么
  • 相关业务概念和历史上下文
  • 可能相关的流程和系统
  • 已有规则和疑似冲突点
  • 初步问题清单
  • RequirementIntent v1 草稿

3. 需求理解卡：让产品确认“是不是这个意思”

需求理解卡不是技术方案，也不是最终规格。它是 AI 对产品意图的复述、假设和待确认问题，目的是防止后面的自动化在错误理解上狂奔。

产品看到的内容示例

我理解这个需求是：当体验课用户转入正式班时，系统需要自动处理原班级关系、正式班入班关系，以及赠课权益。

  • 已消耗的体验课课次是否要扣减？
  • 原有赠课是迁移、清空，还是重新计算？
  • 转班失败后是否允许重新提交？
  • 这个规则只适用于体验课，还是所有转班类型？

我猜测影响：转班申请、班级中心、订单/赠课权益。

产品确认的不是代码锚点，而是：“是的，我要的就是这个业务行为。”确认后系统得到 ConfirmedBusinessGoal、Assumptions 和 OpenQuestions。

4. 影响分析：确认目标后，才进入精确分析

上下文召回问的是“这个需求大概跟什么有关”；影响分析问的是“如果目标已经确认，那么它具体影响哪些业务流、代码入口、状态机、测试、跨服务调用和风险点”。

需要检查
  • 转班申请提交接口
  • 转班执行流程
  • 班级中心入班/出班逻辑
  • 赠课权益服务
  • 订单状态和转班状态机
  • 相关回归测试
给人的展示

这个需求可能影响转班申请服务、班级中心、赠课/订单服务。

风险等级：L2 或 L3。原因：跨服务、涉及权益处理、涉及状态变化。

5. 语义契约：把需求变成可开发、可验证的承诺

系统把确认后的目标、业务规则、影响范围、非目标、验收条件、状态变化和风险等级整理成 Semantic Contract。它是后续开发包、测试计划、MR 校验和记忆回写的共同依据。

这个例子里的契约可能包含
  • 体验课转正式班时，需要处理原班级关系和正式班入班关系
  • 赠课权益不能默认迁移，必须根据产品确认规则处理
  • 已消耗课次需要有明确扣减或保留规则
  • 失败后是否允许重试必须明确
  • 验收必须覆盖正常转班、权益处理、失败重试、跨服务异常

6. 开发、MR 校验与需求变更判断

Agent 或研发根据 Semantic Contract 开发。MR 阶段不只检查代码 diff，而是检查“代码实际做的事情”是否兑现了契约。

代码错了

契约说：体验课已消耗课次不能迁移。代码却把所有课次迁移到了正式班。

处理：MR 打回，要求修代码。

需求理解变了

最初契约说：赠课权益迁移到正式班。开发时产品补充确认：赠课不能迁移，必须重新计算。

处理：生成 SemanticContractChange v2，重新审批，再继续开发。

判断标准很简单：违反已批准契约，是代码错；契约本身被新的业务决策修改，是需求理解变了。

7. Merge 后回写：不是把所有东西塞进图，而是分层沉淀

Merge 后系统把这次需求和代码变更一起进入企业记忆，但不是所有材料都变成业务图节点。原始证据和结构化事实要分层保存。

原始证据进入 Evidence Store
  • 原始需求、需求理解卡、产品确认记录
  • Semantic Contract、技术设计、任务拆分
  • MR 描述、commit diff、review 评论
  • 测试结果、CI 结果、发布记录
  • 线上指标、事故/回滚记录、Agent trace
结构化事实进入业务记忆
  • RequirementIntent
  • BusinessRule 变更
  • BusinessFlow 新增/修改/废弃
  • Acceptance 到 Test 的映射
  • Requirement 到 CodeAnchor 的映射
  • DecisionRecord / GovernanceRule

8. 数据飞轮：下一次会更准

第一轮最难，因为企业记忆少，系统主要靠代码图谱、历史文档和人工确认。确认后，系统学到“这个接口属于转班申请”“这个状态机属于转班流程”“这个赠课调用是权益处理”“这个产品说法对应哪些代码锚点”。

第二次类似需求进入时，AI 可以更快召回已有流程，更少问产品低级问题，影响分析更准，开发包更完整，MR 校验也更严格。这不是训练一个通用模型，而是在训练企业自己的业务语义数据库。

三、关键产物：Semantic Contract

“产品、研发、测试、Agent、CI 和企业记忆共同使用的语义锚点”意思是：大家不再各自理解一份需求，而是围绕同一份被确认的业务承诺工作。

产品用它确认“要什么”，研发用它判断“怎么做”，测试用它生成“怎么验”，Agent 用它执行任务，CI/MR 用它检查实现是否跑偏，企业记忆用它决定 merge 后应该沉淀什么。

产品

确认业务目标、规则边界、非目标和待澄清问题。

Semantic Contract 一份业务承诺，多种角色投影

研发

据此拆设计、拆任务、定位代码影响范围。

测试

把验收条件转成测试计划、回归范围和质量门禁。

Agent

拿它作为开发上下文，执行编码、测试和 MR 生成。

CI / MR

校验代码是否兑现契约，是否引入未声明影响。

企业记忆

merge 后用它组织需求、代码、测试和决策证据。

人看的版本

自然语言说明：目标、规则、影响、非目标、风险、待确认问题。

机器存的版本

结构化记录：验收条件、数据/状态变化、外部契约、证据、版本和风险等级。

四、落地基建：各能力层如何分工

这条链路不是单个 Agent 能完成的，它需要一组基础设施协同。可以把它们理解为从“原始材料”到“业务执行”的几层能力。你的 ht-cbm 和 Vein 就是其中两块关键底座。

1. 数据与证据层

接入需求、文档、会议、MR、代码、测试、日志、指标、事故和用户反馈，保证所有判断都有来源。

2. 代码结构事实层

把多仓代码变成可查询、可版本化、可跨仓追踪的结构事实，如 Route、Method、调用关系、跨服务边、代码片段和结构 diff。ht-cbm 属于这一层

3. 工具与上下文层

通过 MCP / Tool Gateway 让 Agent 能访问代码图谱、业务记忆、GitLab、测试平台、文档系统和观测系统。ht-cbm / Vein 都应作为工具暴露

4. 业务语义与记忆层

维护业务流程、业务实体、业务规则、影响范围、决策记录和长期业务记忆。Vein 属于这一层

5. Semantic Contract Registry

保存语义契约的版本、diff、审批状态、关联需求、关联 MR、验收条件和验证结果，成为链路的中间锚点。

6. Agent Runtime

负责 Agent 编排、任务分解、handoff、工具调用、权限控制、运行状态、失败恢复和 trace 记录。

7. 开发流水线集成

打通 OpenSpec、GitLab、CI、测试生成、MR bot、代码 review 和发布流程，让开发包能进入真实研发环节。

8. 治理与审计层

负责风险分级、审批流、权限控制、证据留存、决策记录、版本回放和发布后反馈闭环。

五、人机协作分级

Human in / on / out of the loop 不应该按流程节点机械划分，而应该按风险和决策性质划分。

L0：低风险 文案、展示、低风险查询。AI 可直接进入开发。
L1：中低风险 单服务、无资金、无权限、无状态机。AI 自动推进，人看 MR 摘要。
L2：中高风险 跨服务、状态变化、关键业务规则。产品或技术 owner 审语义契约。
L3：高风险 资金、权限、合规、数据迁移、删除流程。必须多人审批。
